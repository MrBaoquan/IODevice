## 一、需求概述

### 1.1 业务场景

4D/5D 动感影院从内容制作到放映播控的完整工作流程需要三类工具协同：

| 阶段     | 工具      | 操作者     | 核心功能                               |
| -------- | --------- | ---------- | -------------------------------------- |
| **制作** | IOStudio  | 内容制作   | 编排影片的动感特效、IO 交互时间轴      |
| **放映** | UNIPlayer | 工程师     | 播放影片 + 执行动作文件 + 驱动 IO 设备 |
| **管控** | 播控软件  | 影院操作员 | 选片、播放流程管理、紧急处理、设备监控 |

### 1.2 核心诉求

1. **IOStudio** — 作为制作工具，编排动感影院影片的特效动作 (.motion) 以及其他 IO 交互
2. **UNIPlayer** — 基于 Unity 开发的专用播放器，使用 IOToolkit (IODevice_CSharp_Wrapper) 对 IO 设备与动作文件进行控制
3. **播控软件** — 提供影院操作员使用的 GUI，管理 UNIPlayer 的播控流程（选片、播放、暂停、紧急停止等）

## 三、各端职责边界

### 3.1 IOStudio — 内容制作工具 (已有)

**核心职责：** 编排动感影院影片的特效动作时间轴

| 功能             | 现有状态 | 说明                                        |
| ---------------- | -------- | ------------------------------------------- |
| 多轨道时间轴编辑 | ✅       | 13 个数据模型 + 16 个 ViewModel + 13 个控件 |
| 曲线精编         | ✅       | 4 种插值 + 2D 贝塞尔切线                    |
| 媒体同步预览     | ✅       | LibVLC 视频 + 音频波形 + 节拍检测           |
| .motion 导出     | ✅       | JSON / CSV / CompactJson                    |
| C++ 引擎预览     | ✅       | NativeMotionPlaybackEngine 委托 C++ 求值    |
| 设备 Schema 发现 | ✅       | IODevice.xml 解析                           |
| 撤销/重做        | ✅       | Command 模式，100 级栈                      |

**与 UNIPlayer 的关系：** IOStudio 产出 `.motion` 文件 → UNIPlayer 消费

**不需要改动：** IOStudio 作为离线制作工具，当前架构已完整，三端架构不影响 IOStudio。

### 3.2 UNIPlayer — 放映执行引擎 (已有 Unity 播放器，需增强)

**核心职责：** 播放影片 + 同步执行动作文件 + 驱动 IO 设备

| 功能                      | 说明                                                            |
| ------------------------- | --------------------------------------------------------------- |
| **视频播放**              | Unity VideoPlayer 或 AVPro Video 播放影片                       |
| **动作执行**              | IOToolkit.MotionPlayer.LoadSlot() → PlaySlot() 驱动 IO          |
| **视频-动作同步**         | 视频时间码驱动 MotionSlot.Seek()，保持帧级同步                  |
| **HTTP + WebSocket 服务** | 托管播控 Web 页面 + ws:// 双向命令/状态通道                     |
| **状态广播**              | 定时 WebSocket 推送播放状态 (进度、设备状态、错误) 给播控软件   |
| **影片库管理**            | 扫描本地影片目录，管理 video + .motion 资源映射 + REST API 查询 |
| **安全保护**              | 紧急停止 → MotionPlayer.StopAll() + 平台回中                    |

**IOToolkit 集成点 (已有 API，零改造)：**

```csharp
// UNIPlayer 中的 IOToolkit 使用示例
using IOToolkit;

public class CinemaPlaybackManager : MonoBehaviour
{
    private MotionSlot _currentSlot;

    void Start()
    {
        IODeviceController.Instance.Load();  // 加载 IODevice.xml
    }

    void Update()
    {
        IODeviceController.Instance.Update();  // 驱动 IO 刷新 + MotionPlayer Tick
    }

    // 播控软件命令 → 加载影片
    public void LoadFilm(string filmId, string motionPath)
    {
        _currentSlot = MotionPlayer.LoadSlot(filmId, motionPath);
    }

    // 播控软件命令 → 播放
    public void Play()
    {
        _currentSlot?.Play();
        videoPlayer.Play();  // 同步启动视频
    }

    // 播控软件命令 → 紧急停止
    public void EmergencyStop()
    {
        MotionPlayer.StopAll();  // 500ms smoothstep 回中
        videoPlayer.Stop();
    }
}
```

**需要新增的功能：**

| 新增功能              | 复杂度 | 说明                                                    |
| --------------------- | ------ | ------------------------------------------------------- |
| HTTP + WebSocket 服务 | 中     | EmbedIO NuGet 包，同时提供静态文件托管 + WebSocket 端点 |
| 状态广播服务          | 低     | 50ms 定时 WebSocket 推送播放进度 + 设备状态             |
| REST API (影片库)     | 低     | GET /api/films 返回影片列表 + 缩略图 URL                |
| 影片库扫描            | 低     | 扫描指定目录，建立 film → (video, motion) 映射          |
| 视频-动作同步逻辑     | 中     | 视频帧回调 → MotionSlot.Seek() 保持同步                 |

### 3.3 播控软件 — 运营管理终端 (新建)

**核心职责：** 为影院操作员提供 GUI，远程管理 UNIPlayer 的播放流程

**界面设计 (基于 播控软件.pen 原型)：**

| 界面                 | 功能                                                 |
| -------------------- | ---------------------------------------------------- |
| **1-待机界面**       | 展馆品牌展示 + 触摸屏幕启动                          |
| **2-影片选择界面**   | 分类浏览 + 影片卡片 (缩略图/时长/评分) + 分页        |
| **2.5-播放准备引导** | 确认选片 + 安全检查流程 (关闭舱门/系安全带/检查设备) |
| **3-影片播放界面**   | 播放进度条 + 暂停/继续 + 进度控制                    |
| **4-紧急处理界面**   | 紧急暂停 + 平台状态 + 强制停止 + 恢复播放 + 返回选片 |
| **5-影片结束界面**   | 播放完成确认 + 重新播放 / 返回选片 / 返回待机        |
| **6-监控界面**       | 设备实时状态 + 视频预览 + 多摄像头 + 日志            |
| **7-高级控制面板**   | 手动平台轴控制 + 特效设备开关 + 姿态监控 + 程序控制  |

**核心特征：**

- 1920×1080 全屏 Kiosk 模式 (暗色影院风格)
- 触屏友好 (大按钮、简洁流程)
- 纯 WebSocket Client — 不直接接触 IODevice，所有控制通过 UNIPlayer 代理
- 状态展示驱动 — 被动接收 UNIPlayer 的状态广播
- 跨终端 — Windows Kiosk + iPad/Android 平板均需支持

## 四、通信架构设计

### 4.1 通信拓扑

```
播控软件 (任意终端)          UNIPlayer                    IODevice 硬件
┌──────────┐  WebSocket     ┌──────────┐    P/Invoke     ┌──────────┐
│ WS       │  ws://ip:9600  │ WS       │ ──SetDO()────→ │ 动感平台  │
│ Client   │ ──命令──────→ │ Server   │ ←─DI/AI Query── │ 风机/灯光 │
│ (浏览器) │ ←─状态推送──── │ (Unity)  │                  │           │
└──────────┘                └──────────┘                  └──────────┘
 Win/iPad/Android               Unity 放映引擎               物理设备
```

### 4.2 命令协议

采用 WebSocket + JSON 协议，UNIPlayer 内建 WebSocket Server (ws://ip:9600)。

> **为何选 WebSocket 而非 TCP？** 播控软件需支持平板 (iPad/Android) 部署，WebSocket 是浏览器原生支持的唯一全双工协议。同时 WebSocket 天然帧边界，无需处理 TCP 粘包问题。UNIPlayer 侧可同时保留 TCP:9600 用于 IOStudio 等桌面端直连。

**帧格式：** WebSocket Text Frame + UTF-8 JSON body (无需长度前缀)

**播控命令集：**

```json
// ── 影片管理 ──
{ "cmd": "list_films" }
{ "cmd": "load_film", "film_id": "jurassic_adventure" }
{ "cmd": "unload_film" }

// ── 播放控制 ──
{ "cmd": "play" }
{ "cmd": "pause" }
{ "cmd": "resume" }
{ "cmd": "stop" }
{ "cmd": "seek", "time_ms": 30000 }
{ "cmd": "emergency_stop" }

// ── 设备控制 (高级面板) ──
{ "cmd": "set_do", "device": "Platform-0", "key": "OAxis_00", "value": 0.5 }
{ "cmd": "device_status" }

// ── 系统 ──
{ "cmd": "heartbeat" }
{ "cmd": "get_status" }
```

**状态推送 (UNIPlayer → 播控软件, 50ms 周期)：**

```json
{
  "type": "status",
  "state": "playing",
  "film_id": "jurassic_adventure",
  "film_name": "侏罗纪冒险",
  "current_time_ms": 45230,
  "duration_ms": 180000,
  "video_state": "playing",
  "devices": {
    "Platform-0": { "connected": true, "axes": [0.5, 0.3, 0.7, 0.5, 0.5, 0.5] },
    "Fan-0": { "connected": true },
    "Light-0": { "connected": true }
  },
  "errors": []
}
```

### 4.3 通信协议选型对比

| 方案           | 浏览器/平板   | 桌面端 | 天然帧边界 | 双向实时 | Unity 集成 | 适用性 |
| -------------- | ------------- | ------ | ---------- | -------- | ---------- | ------ |
| **WebSocket**  | ✅ 原生       | ✅     | ✅         | ✅       | 中 (NuGet) | ⭐⭐⭐ |
| **TCP + JSON** | ❌            | ✅     | ❌ 需粘包  | ✅       | ✅ 原生    | ⭐⭐   |
| **HTTP SSE**   | ✅            | ✅     | ✅         | ❌ 单向  | 低         | ⭐     |
| **gRPC-Web**   | ✅ (grpc-web) | ✅     | ✅         | ✅       | 困难       | ⭐     |
| **MQTT**       | ✅ (ws)       | ✅     | ✅         | ✅       | 中         | ⭐⭐   |

**推荐：WebSocket + JSON**

- 浏览器/平板原生支持 (`new WebSocket('ws://...')`) — 播控软件可跑在任意带浏览器的设备上
- 天然帧边界，无 TCP 粘包问题
- 全双工：命令 (Client→Server) + 状态推送 (Server→Client) 在同一连接
- Unity 侧使用 [websocket-sharp](https://github.com/sta/websocket-sharp) 或 NativeWebSocket (轻量 NuGet 包)
- JSON 文本协议人类可读，浏览器 DevTools 直接调试
- 向下兼容：UNIPlayer 可同时保留 TCP:9600 端口给 IOStudio 等桌面端工具

## 五、数据流分析

### 5.1 完整工作流

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 制作阶段                                                                │
│                                                                         │
│  [内容制作] → IOStudio 时间轴编辑 → 导出 .motion 文件                   │
│              ↓                                                          │
│  打包: video.mp4 + effect.motion + manifest.json → 影片资源包           │
│              ↓                                                          │
│  部署到放映机 (USB / 局域网文件共享)                                     │
└──────────────────────────────────┬──────────────────────────────────────┘
                                   ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 放映阶段                                                                │
│                                                                         │
│  ① 操作员启动 UNIPlayer → 扫描影片库 → TCP Server 就绪                  │
│  ② 操作员打开播控软件 → TCP 连接 UNIPlayer → 获取影片列表              │
│  ③ 操作员选择影片 → 播控命令 load_film → UNIPlayer 加载资源             │
│  ④ 安全检查流程 → 播控命令 play → UNIPlayer 同步播放视频+动作           │
│  ⑤ 播放中: 状态推送 → 播控软件更新进度/设备状态                         │
│  ⑥ 播放完毕 / 紧急停止 → 平台回中 → 播控软件展示结束/紧急界面          │
│  ⑦ 循环 ② → ⑥                                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5.2 关键数据流

| 数据流       | 方向                      | 载体           | 频率         |
| ------------ | ------------------------- | -------------- | ------------ |
| .motion 文件 | IOStudio → 文件系统       | 文件导出       | 离线         |
| 影片资源包   | 文件系统 → UNIPlayer      | 本地文件扫描   | 启动时       |
| **播控命令** | 播控软件 → UNIPlayer      | WebSocket JSON | 事件驱动     |
| **状态推送** | UNIPlayer → 播控软件      | WebSocket JSON | 50ms (20Hz)  |
| IO 输出      | UNIPlayer → IODevice 硬件 | P/Invoke SetDO | 每帧 (~16ms) |
| 视频画面     | UNIPlayer → 投影/屏幕     | GPU 渲染输出   | 每帧 (~16ms) |

## 六、播控软件 GUI 技术选型

### 6.1 需求约束分析

从 播控软件.pen 设计稿提取的 UI 需求特征：

| 维度           | 需求                                                   |
| -------------- | ------------------------------------------------------ |
| **分辨率**     | 1920×1080 全屏 Kiosk 模式                              |
| **风格**       | 暗色影院主题，渐变边框，发光高亮                       |
| **交互方式**   | 触屏 + 鼠标/键盘                                       |
| **界面数量**   | 8 个核心界面 (待机/选片/准备/播放/紧急/结束/监控/高级) |
| **数据展示**   | 影片卡片列表 + 实时进度条 + 设备状态面板 + 摄像头预览  |
| **控件复杂度** | 滑块 (Slider) + 按钮 + 卡片 + 进度条 + 状态指示灯      |
| **动态性**     | 实时状态刷新 (50ms 推送) + 播放进度动画                |
| **网络**       | WebSocket Client (连接 UNIPlayer)                      |
| **目标平台**   | Windows 工控机 + iPad/Android 平板 (未来)              |
| **操作员水平** | 非技术人员，需极简操作流程                             |

### 6.2 候选技术对比

> **核心约束变化：** 播控软件未来需部署到 iPad/Android 平板，这直接淘汰了仅桌面端的方案 (WPF)，并大幅提升 Web 方案的权重。

### 6.4 技术选型推荐

**推荐方案：Web 应用 (Vue 3 + WebSocket + Tauri 2)** ⭐

考虑平板部署需求且不限团队技术栈，**纯 Web 方案以压倒性优势胜出** (9.65 vs 第二名 Flutter 8.15)。

**核心理由：**

1. **平板零成本部署** — iPad/Android 平板打开浏览器输入 `http://uniplayer-ip:9600` 即用，无需安装任何 App，无需过 App Store 审核
2. **暗色影院 UI 最自然** — CSS 渐变/阴影/发光/动画/毛玻璃效果是 Web 的天然能力，设计稿 (播控软件.pen) 中的所有视觉效果都可用 CSS 一比一还原
3. **WebSocket 原生** — `new WebSocket('ws://...')` 一行代码建立双向实时连接，50ms 状态推送完美适配
4. **部署即更新** — UNIPlayer 内嵌轻量 HTTP 服务 (serve 静态文件)，播控 Web 页面随 UNIPlayer 一起部署，平板刷新浏览器即获取最新版本
5. **响应式布局** — CSS Media Query / Container Query 天然适配 1920×1080 (Windows Kiosk) 和 iPad (2048×1536) 两种分辨率
6. **Windows Kiosk 模式** — Chrome `--kiosk --app=http://localhost:9600` 全屏无边框运行，或用 Tauri (~5MB) 封装为独立 exe

#### 6.5.3 Quasar Framework 专项分析

**Quasar 2** 是基于 Vue 3 的全栈跨平台框架，内置 70+ Material Design 组件，自带 CLI 可从同一代码库一键发布到 SPA / SSR / PWA / Electron (桌面) / Capacitor (移动端) / 浏览器扩展六个目标。

**Quasar 的优势：**

- **一体化 CLI** — `quasar dev -m capacitor -T android` 一条命令启动 Android 开发，无需手动集成 Capacitor
- **内置 70+ 组件** — 按钮/对话框/表格/滑块/通知全部开箱即用，无需引入第三方 UI 库
- **暗色模式** — `$q.dark.set(true)` 一行代码全局切换，Material Design 暗色变体完整
- **跨平台统一** — 同一代码 + `$q.platform.is.mobile` 判断平台差异，逻辑共享率极高

**Quasar 在本项目的劣势：**

| 问题                         | 影响                                                                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Material Design 风格锁定** | 播控软件.pen 设计稿是暗色影院风格 (渐变边框/发光效果/圆角大按钮)，与 Material Design 扁平风格差异大，深度定制 Quasar 组件的工作量可能超过从零用 Tailwind 构建 |
| **桌面封装 = Electron**      | Quasar CLI 官方桌面方案是 Electron (~150MB)，不支持 Tauri。要用 Tauri 需绕过 Quasar CLI，失去一体化优势                                                       |
| **组件库封闭生态**           | Quasar 组件与 Naive UI / PrimeVue 等 Vue 生态库不兼容 (样式系统冲突)，选了 Quasar 就锁死在其组件体系内                                                        |
| **Bundle 较大**              | Quasar 全量引入 ~120KB gzip (Vue 3 裸框架仅 ~33KB)，Tree-shaking 后仍约 80KB                                                                                  |
| **中文社区偏小**             | 国内 Quasar 使用者远少于 Vue 3 + 独立组件库的主流路线，疑难问题中文资料少                                                                                     |

**结论：Quasar 适合「Material Design 风格 + 快速原型 + 不需要 Tauri」的项目。对于本项目，暗色影院定制 UI + Tauri 2 轻量桌面封装的需求使得 Quasar 的核心优势（Material 组件 + Electron CLI）反而成为约束。**

#### 6.5.4 AI 时代的生态重要性重估

> **用户关注：** 在 AI 辅助编程时代 (Copilot / Cursor / Claude)，「生态大小」和「社区资源」是否还重要？小众框架是否同样可行？

**AI 确实改变了部分等式：**

| 传统痛点                   | AI 时代改善                           | 残留影响                      |
| -------------------------- | ------------------------------------- | ----------------------------- |
| **查 API 文档**            | ✅ AI 直接生成代码，无需翻文档        | 几乎消除                      |
| **搜 StackOverflow 排错**  | ✅ AI 可诊断多数常见错误              | 大幅缓解                      |
| **学习曲线**               | ✅ AI 可生成完整示例、解释概念        | 大幅缓解                      |
| **样板代码 (boilerplate)** | ✅ AI 一键生成组件/路由/状态管理      | 几乎消除                      |
| **底层 Bug / 框架缺陷**    | ❌ AI 无法修复框架本身的 Bug          | **不变** — 仍依赖社区维护     |
| **WebView 兼容性问题**     | ❌ AI 无法解决浏览器/WebView 渲染差异 | **不变** — 需要真实设备调试   |
| **第三方库版本冲突**       | ❌ AI 对依赖链冲突的解决能力有限      | **不变** — 小生态依赖链更脆弱 |
| **安全漏洞响应速度**       | ❌ 社区小 = 安全补丁慢                | **不变** — 工控场景不可忽视   |
| **长期维护 (5年+)**        | ❌ AI 不能保证框架不停止维护          | **不变** — 小社区框架风险更高 |

**结论：AI 消除了「信息获取」层面的生态优势 (~40%)，但「框架质量 / Bug 修复速度 / 长期维护保障」仍由社区规模决定 (~60%)。**

对于本项目的实际影响：

1. **Svelte / Solid 变得更可行了** — AI 可以弥补文档/示例少的短板，如果团队追求极致性能可以考虑
2. **Quasar 不因 AI 变得更优** — 其劣势 (Material 风格锁定、Electron 桌面、封闭生态) 是架构层面的，AI 无法改变
3. **Vue 3 的优势部分弱化但仍存在** — 中文社区优势被 AI 削弱 (AI 直接回答问题)，但 Naive UI 组件质量、Tauri 官方集成这些不受 AI 影响
4. **最终选型权重调整：** 「生态大小」从原来的 15% 降低到 ~8%，但「框架架构适配度」和「长期维护保障」权重相应提升

**调整后结论不变：Vue 3 + Tauri 2 仍是最优解。** 原因从 "生态最大" 转变为 "架构最适配" — Vue 3 的模板响应式 + Naive UI 暗色主题 + Tauri 2 全平台支持，这些是 AI 无法替代的结构性优势。

```ts
// composables/useWebSocket.ts — WebSocket 连接管理
import { ref, onUnmounted } from "vue";

export function useWebSocket(url: string) {
  const connected = ref(false);
  let ws: WebSocket | null = null;
  let reconnectTimer: number;

  function connect() {
    ws = new WebSocket(url);
    ws.onopen = () => {
      connected.value = true;
    };
    ws.onclose = () => {
      connected.value = false;
      reconnectTimer = window.setTimeout(connect, 2000); // 2s 自动重连
    };
    ws.onmessage = (e) => {
      const msg = JSON.parse(e.data);
      // → dispatch to Pinia store
    };
  }

  function send(cmd: object) {
    ws?.send(JSON.stringify(cmd));
  }

  connect();
  onUnmounted(() => {
    ws?.close();
    clearTimeout(reconnectTimer);
  });

  return { connected, send };
}
```

### 6.6 性能分析 — Web 方案能否满足实时需求

> **核心问题：** 播控软件通过 WebSocket 接收 50ms (20Hz) 状态推送，Web UI 能否实时无卡顿地渲染？

#### 6.6.1 播控软件的性能需求量化

| 指标                   | 需求值         | 说明                                 |
| ---------------------- | -------------- | ------------------------------------ |
| **状态推送频率**       | 20Hz (50ms/帧) | UNIPlayer 每 50ms 推送一次完整状态   |
| **UI 刷新帧率**        | ≥30fps (≥33ms) | 操作员可感知的流畅阈值               |
| **命令响应延迟**       | <100ms         | 按下按钮→UNIPlayer 收到命令          |
| **紧急停止响应**       | <200ms         | 从触屏到 MotionPlayer.StopAll() 执行 |
| **同时可见 DOM 节点**  | <500           | 单屏最多 ~20 张影片卡片 + 状态面板   |
| **WebSocket 消息体积** | ~500 bytes/帧  | JSON 状态 (6 轴值 + 设备状态 + 进度) |
| **内存占用目标**       | <200MB         | 长时间运行 (8h+) 不泄漏              |

#### 6.6.2 Web 技术性能基准

| 操作                       | 耗时     | 与需求对比            |
| -------------------------- | -------- | --------------------- |
| WebSocket.onmessage 触发   | <0.1ms   | ✅ 远超 50ms 需求     |
| JSON.parse (500 bytes)     | ~0.02ms  | ✅ 几乎零开销         |
| Vue reactive state 更新    | ~0.1ms   | ✅ 信号级更新         |
| DOM patch (进度条+6轴值)   | ~0.5ms   | ✅ 远低于 16ms 帧预算 |
| CSS transition 动画        | GPU 加速 | ✅ 不占 JS 主线程     |
| 完整 20 张影片卡片列表渲染 | ~5ms     | ✅ 首屏 <16ms         |

**50ms 推送场景的逐帧开销：**

```
WebSocket.onmessage       0.1ms
JSON.parse(500B)          0.02ms
Pinia store update        0.1ms
Vue DOM patch (进度条)    0.5ms
─────────────────────────────
总计                      ~0.72ms / 帧

帧预算 (30fps):           33ms
利用率:                   2.2%   ← 几乎空闲
```

**结论：性能完全不是瓶颈。** 播控软件的 UI 复杂度 (几十个 DOM 节点变化) 远低于 Web 框架的性能天花板 (如 React/Vue 可处理数千节点 60fps 更新)。

#### 6.6.3 性能风险场景与缓解

| 风险场景                     | 分析                                     | 缓解措施                                               |
| ---------------------------- | ---------------------------------------- | ------------------------------------------------------ |
| **50ms 推送下 DOM 抖动**     | Vue/React diff 对少量节点更新极快 (<1ms) | 进度条用 CSS `transition` 平滑，不逐帧 rerender        |
| **影片列表大量缩略图加载**   | 100 张缩略图 ≈ 10MB，影响首屏            | 懒加载 (`loading="lazy"`) + 缩略图压缩到 50KB/张       |
| **监控页面多路摄像头流**     | MJPEG/HLS 解码消耗 CPU                   | `<img>` 标签 MJPEG 由浏览器原生解码；限制 4 路同时显示 |
| **长时间运行内存泄漏**       | WebSocket 消息缓存/事件监听器未清理      | 不缓存历史状态 (仅保留最新帧)；组件 onUnmounted 清理   |
| **Android 低端设备 WebView** | 系统 WebView 版本可能较旧                | 要求 Android 10+ (WebView 80+)；Tauri 2 自动检查       |
| **Windows 高 DPI 缩放**      | 4K 屏幕缩放可能导致布局错位              | CSS `rem` 单位 + viewport meta + Tauri window 配置     |

#### 6.6.4 与原生方案的性能对比

| 指标                | Web (Vue 3)      | 原生 (Avalonia/WPF) | 差异             |
| ------------------- | ---------------- | ------------------- | ---------------- |
| **启动时间**        | ~300ms (SPA)     | ~800ms (CLR 启动)   | Web 更快         |
| **20Hz 状态刷新**   | ~0.7ms/帧        | ~0.3ms/帧           | 差异不可感知     |
| **内存占用**        | ~80MB (WebView)  | ~60MB (.NET)        | 差 20MB，可接受  |
| **紧急按钮响应**    | ~10ms (touch→WS) | ~5ms (click→TCP)    | 差 5ms，不可感知 |
| **CSS 动画流畅度**  | 60fps (GPU)      | 60fps (GPU)         | 相同             |
| **CPU 占用 (空闲)** | ~2%              | ~1%                 | 差异极小         |

**结论：对于播控软件这类「低频更新 + 少量 DOM + 按钮驱动」的应用，Web 与原生的性能差距完全不可感知。** 真正的性能敏感代码在 UNIPlayer (Unity) 和 IODevice.dll (C++) 中 —— 播控 UI 只是遥控器。

#### 6.6.5 性能保障最佳实践

```vue
<!-- ProgressBar.vue — 高性能进度条 (CSS transition 驱动, 非逐帧 JS 更新) -->
<template>
  <div class="h-2 bg-gray-800 rounded-full overflow-hidden">
    <div
      class="h-full bg-blue-500 rounded-full transition-[width] duration-100 ease-linear"
      :style="{ width: progressPercent + '%' }"
    />
  </div>
</template>

<script setup lang="ts">
import { computed } from "vue";
import { usePlaybackStore } from "@/stores/playback";

const store = usePlaybackStore();
const progressPercent = computed(() =>
  store.durationMs > 0 ? (store.currentTimeMs / store.durationMs) * 100 : 0,
);
</script>
```

关键优化点：

1. **进度条用 CSS `transition` 而非 JS 逐帧更新** — 浏览器 GPU 合成层处理，零 JS 开销
2. **状态推送不缓存历史** — Pinia store 仅保留最新一帧，无内存累积
3. **影片缩略图懒加载** — 可视区域外的图片不加载，减少首屏压力
4. **设备状态面板用 `v-memo`** — 仅在值变化时更新对应 DOM 节点
5. **WebSocket 重连使用指数退避** — 避免断连风暴

### 8.3 关键设计决策

| 决策                                            | 理由                                                                  |
| ----------------------------------------------- | --------------------------------------------------------------------- |
| **播控软件不加载 IODevice.dll**                 | IODevice.dll 单例限制 + 架构解耦 — 播控端纯 GUI + WebSocket 通信      |
| **UNIPlayer 作为 WebSocket Server (非 Client)** | UNIPlayer 是设备持有者，应是被动服务端；播控软件随时可重启不影响放映  |
| **WebSocket 替代 TCP**                          | 浏览器原生支持，天然帧边界无粘包，一套协议同时服务桌面和平板          |
| **状态推送而非轮询**                            | UNIPlayer 主动推送 50ms 状态，播控软件被动渲染，减少网络往返          |
| **影片资源包由 UNIPlayer 管理**                 | 视频文件在 UNIPlayer 本地才有意义；播控软件仅展示元数据               |
| **紧急停止双保险**                              | 播控软件发送 emergency_stop + UNIPlayer 本地 watchdog 双重保护        |
| **播控软件使用 Web (Vue 3 + Tauri 2)**          | 平板零安装 + Tauri 2 打包 Windows EXE + Android APK，一套代码三端发布 |
| **UNIPlayer 内嵌 HTTP+WS 服务**                 | 播控页面随 UNIPlayer 部署，平板开浏览器即最新版本，零运维             |

## 十、结论与建议

### 10.1 可行性结论

**该三端架构完全可行。** 核心依据：

1. **IOToolkit C# Wrapper API 已完备** — 22 个 DllImport 覆盖全部播控需求，UNIPlayer 作为 Unity 应用使用 IOToolkit 是已验证的成熟路径 (IOToolkit_UE4_Plugin 已证明游戏引擎集成可行性)
2. **TCP 通信基础设施已存在** — IOStudio 的 `ConnectionManager` + `TcpServerSender` 提供了可复用的 TCP 协议代码，TCP MotionServer 协议 (4B 长度前缀 + JSON) 已完成设计
3. **.motion 格式已统一** — C#/C++ 字段名一致、Bezier 语义已对齐，IOStudio 导出的 .motion 文件可直接被 UNIPlayer (通过 IOToolkit) 加载播放
4. **职责边界清晰** — IOStudio 专注制作、UNIPlayer 专注放映、播控软件专注管控，三端通过文件和 TCP 松耦合

### 10.2 技术选型结论

**播控软件推荐使用 Vue 3 + Tauri 2 (WebSocket 通信)。** 核心理由：

- **跨平台发布**：Tauri 2 从同一代码库输出 Windows EXE (~5MB)、Android APK (~8MB)、纯 Web 页面
- **性能充裕**：50ms 推送下 UI 刷新仅占 ~0.7ms (帧预算利用率 2.2%)，与原生方案差距不可感知
- **平板零安装**：纯浏览器访问 UNIPlayer HTTP 服务，即开即用
- **学习成本低**：Vue 3 模板语法 + Pinia 状态管理对 C# 团队最友好
- **部署即更新**：UNIPlayer 内嵌 HTTP 服务托管 Web 资源，版本随放映端同步
